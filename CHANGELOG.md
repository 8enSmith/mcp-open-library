# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]
### Added
- `get_work`, which returns the full record for an Open Library work — the book as a whole, across all its editions: description, subjects, subject places, people and times, first publication date, cover, excerpts, external links, and authors with their names. Until now `search_books`, `get_book_by_title` and `get_book_by_id` returned an `open_library_work_key` that no tool accepted. Author names come from one extra search request; if that request fails, the authors are still returned by key rather than the tool failing. No edition count is reported, because the search index's count can disagree with the editions endpoint; `get_work_editions`' `num_found` is the authoritative total
- `get_work_editions`, which lists a work's editions — its specific printings — each with its `edition_key`, title, edition name, publishers, publish date, languages (as the 3-letter MARC codes `search_books`' `language` takes), first ISBN-13 and ISBN-10 with separators removed, page count, format and cover. It returns at most `limit` editions (default 20, maximum 100) with `num_found`, the total, and pages with `offset`. A page of 50 raw edition records is ~37KB, mostly source records, local IDs and revision stamps; the trimmed page is ~13KB. Editions come in Open Library's order, not by date, and the endpoint offers no filter. Each `edition_key` can be passed to `get_book_by_id` as `{ "idType": "olid" }` for that edition's full record
- Both tools accept the work key bare (`OL45804W`) or in the `/works/OL45804W` form the other tools return, and every key they report is bare. A work Open Library has merged into another is followed to the surviving work, whose key is reported as `work_key`. Merged works answer with a redirect record rather than an HTTP redirect, and the editions endpoint answers 404 for them, so without this they would have been reported as not found
- The `search_books` and `get_book_by_title` descriptions now say that a result's `open_library_work_key` can be passed to the two new tools

## [1.2.7] - 2026-11-21
### Added
- One-click install buttons for Cursor, VS Code and VS Code Insiders in the README, and a `claude mcp add` command for Claude Code. Each button goes through the editor's HTTPS redirect (`cursor.com/install-mcp`, `vscode.dev/redirect/mcp/install`) rather than linking to the `cursor://` or `vscode:` scheme directly, because GitHub strips links with custom schemes from rendered Markdown. All of them run the same `npx -y mcp-open-library` command as the `{"command": "npx", "args": ["-y", "mcp-open-library"]}` config the Quick Start shows, with the VS Code links also setting `"type": "stdio"`, and that JSON block stays the first launch command in the Installation section so scrapers such as mcp.so keep picking it up

### Changed
- Updated `vitest` from `^3.1.1` to `^5.1.1`, and `@types/node` from `^20.11.24` to `^22.20.5` to go with it. vitest 5 declares `@types/node` as an optional peer dependency with the range `^22.0.0 || >=24.0.0`, and npm enforces an optional peer's range whenever that package is installed, so the vitest update alone made `npm ci` fail with `ERESOLVE`. The Node 22 types also match the runtime: `.nvmrc` pins `v22.23.4`, and both CI workflows install from it, so the build had been type-checking against Node 20's APIs while running on Node 22. `tinypool` drops out of the tree, because vitest 5 no longer uses it. The `Server` mock in `src/index.test.ts` is now a `function` expression rather than an arrow function. Since vitest 4, a mock called with `new` calls its implementation with `new`, and an arrow function cannot be constructed, so every test in that file failed with `mockServer is not a constructor`. Both packages are development dependencies, so nothing in the published package changes

### Security
- Updated `axios` from `^1.19.0` to `^1.21.1` and `zod` from `^4.3.6` to `^4.6.6`, and updated `follow-redirects` from 1.16.0 to 1.16.3, `fast-uri` from 3.1.5 to 3.1.9, `body-parser` from 2.3.0 to 2.4.0 and `js-yaml` from 4.3.1 to 4.3.2 in the lockfile. Together these clear all 18 open high-severity Dependabot alerts. `axios` has to reach 1.21.1, not only 1.20.0, its first patched release. 1.21.1 is the first release that requires `follow-redirects ^1.16.2`. Earlier releases accept `^1.16.0`, so the locked `follow-redirects` 1.16.0 would have stayed, with its three alerts. `axios` and `follow-redirects` are the two on a path the server uses: cover and author photo lookups follow a redirect from `covers.openlibrary.org` to the Internet Archive. The `follow-redirects` fixes stop credential headers from following a redirect to another origin, and the server sends none, only a `User-Agent`. `body-parser` is reached only through the SDK's HTTP transport, which this server never loads, because it runs only over `StdioServerTransport`. The server's own zod argument schemas contain no collections, which is where the `zod` advisory lies. `js-yaml` is a development dependency. `body-parser` 2.4.0 also requires newer `qs` and `content-type`, and `qs` 6.17.1 clears three medium-severity alerts as well. The new `axios` and `zod` minimums are what reach anyone installing the package. The lockfile is not published, so `npx mcp-open-library` resolves dependencies from the ranges in `package.json`. The old ranges allowed the fixed versions but did not require them, so a project whose own lockfile pinned an older `axios` or `zod` could keep the vulnerable copy. With the raised minimums, npm now has to install a fixed version. That includes `follow-redirects` 1.16.2 or later, which `axios` 1.21.1 requires. `fast-uri` and `body-parser` come in through `@modelcontextprotocol/sdk`, and `js-yaml` is a development dependency, so this server's own manifest cannot set a minimum for those three. The lockfile update covers this repository's own development and CI installs
- Refreshed the lockfile within the existing `package.json` ranges, which clears the remaining 21 open Dependabot alerts: 20 medium-severity and 1 low-severity. `hono` goes from 4.13.1 to 4.13.19 (ten alerts, including the low one), `ip-address` from 10.5.0 to 10.7.6 (five), and `@hono/node-server` from 2.1.0 to 2.1.11 (three). All three come in through `@modelcontextprotocol/sdk`, which goes from 1.32.0 to 1.32.2, and `ip-address` comes through the SDK's `express-rate-limit`, which goes from 8.6.2 to 8.7.5. Within the SDK, `@hono/node-server` is imported only by the Streamable HTTP server transport, `hono` only by an example server, and `express-rate-limit` only by the OAuth handlers. This server imports only `server/index.js`, `server/stdio.js` and `types.js`, and the only packages outside the SDK that those load are `ajv`, `ajv-formats`, `zod` and `zod-to-json-schema`. `minimatch` goes from 10.2.6 to 11.0.9 (one alert). Its first patched release is 11.0.1, and `@typescript-eslint/typescript-estree` 8.67.0 accepts only `^10.2.2`, so that fix needed `@typescript-eslint/*` to go from 8.67.0 to 8.73.0, the first release that requires `^11.0.1`. Both copies of `brace-expansion` are updated as well: 1.1.18 to 1.1.22 and 5.0.9 to 5.0.13 (two alerts). `minimatch`, `brace-expansion` and `@typescript-eslint/*` are development dependencies. `package.json` is unchanged, because raising a minimum there would not help anyone installing the package. SDK 1.32.2 still declares `hono ^4.11.4`, so requiring it would not force a fixed `hono`, and the other affected packages are not direct dependencies. A fresh install already resolves fixed versions from the existing ranges. The refresh also moves packages that no alert required. On the runtime side, `express` goes from 5.2.1 to 5.3.0, which brings `content-disposition` 1.1.0 to 2.0.1 (a major version, required by `express` 5.3.0), and minor updates to `router`, `negotiator`, `on-finished`, `encodeurl` and `content-type`, along with `jose` 6.2.8 to 6.2.18. All of these come in through the SDK, and none is loaded over stdio: the stdio path never imports `express` or `jose`. On the development side, `prettier` goes from 3.9.6 to 3.10.1, and `src` still passes `prettier --check` unchanged, with small updates to `acorn`, `semver`, `yaml` and other tooling packages

## [1.2.6] - 2026-10-22
### Security
- Updated `@modelcontextprotocol/sdk` from `^1.30.0` to `^1.32.0`, which fixes two high-severity advisories. [CVE-2026-111767](https://github.com/advisories/GHSA-22jm-h49p-29qw) (missing authorization, 1.24.0 up to 1.32.0) let one session read, modify or collect the results of tasks created by another session, through the SDK's `InMemoryTaskStore` on a shared HTTP server. [CVE-2026-111769](https://github.com/advisories/GHSA-6prh-2h8m-c8cw) (open redirect, below 1.32.0) made the SDK's HTTP client follow redirects to a different origin, so a malicious server could have OAuth credentials and tokens sent to a host it controlled. Neither was reachable from this server. It runs only over `StdioServerTransport`, never passes a `taskStore` to `Server`, and does not use the SDK's client, OAuth or HTTP transports. The update clears the Snyk findings against the dependency tree. The SDK's own dependency ranges did not change between the two versions, so nothing else in the lockfile moved. The regenerated lockfile also records the root `bin` as `mcp-open-library`. `package.json` was renamed in 1.2.0, but the lockfile was never updated and still listed `open-library-server`. That field has no effect on installs

## [1.2.5] - 2026-10-22
### Security
- The Node version in `.nvmrc` is now `v22.23.4`, up from `v22.21.1`, in response to the October 2026 compromise of eight eMudhra (emSign) intermediate certificate authorities. Node carries its own copy of the trusted root certificates, and releases on the 22 line before 22.23.4 still trust the compromised chain, so anyone holding a certificate issued from it could impersonate any HTTPS site to that Node — the npm registry and the Open Library API included. Both CI workflows install Node from `.nvmrc`, which meant the release pipeline was running `npm ci` and `npm publish` on an affected version. Nothing in the published package changes, but if you run this server yourself, run it on Node 22.23.4, 24.22.1 or 26.12.1 or later: it calls Open Library through Node's built-in trust store, so the Node you start it with decides whether it is exposed
- The `Dockerfile` is now based on `debian:bookworm-slim` rather than `debian:bullseye-slim`. Bullseye offers no fixed `ca-certificates` package: the newest available, `20250419~deb12u1~deb11u1`, still trusts the compromised chain, whereas bookworm's `20250419~deb12u2` rejects it. Bullseye's security packages were also returning 404 from `deb.debian.org`, so the image could no longer be built at all. The system trust store covers the build steps that download installers and source over HTTPS (NodeSource, uv and the `git clone`); the running server uses the Node that NodeSource installs, which is now 22.23.4. This changes only `docker build` as described in the README — Glama builds its own generated Dockerfile, which was already on bookworm

## [1.2.1] - 2026-08-14
### Added
- `glama.json`, claiming maintainership of this server's [Glama](https://glama.ai) listing. Glama does not build the `Dockerfile` committed here: it builds one generated from a build spec — base image, Node version, build steps and `CMD` arguments — held in its admin page, and a Dockerfile is [either "authored by the maintainer and checked into the repository, or inferred by Glama's AI-assisted build system"](https://glama.ai/mcp/methodology). This listing is on the inferred path, and the two have drifted apart: the generated file uses `debian:bookworm-slim` and `mcp-proxy@6.4.3` against the committed file's `debian:bullseye-slim` and `mcp-proxy@2.10.6`, so editing the committed `Dockerfile` does not change what Glama builds. Claiming maintainership is what grants access to the spec that does, and to the button that re-runs a build — which is the whole remedy when a build fails for reasons outside the repository, as the last one did when Glama's builder timed out resolving its base image from Docker Hub before reaching any of this code. The [schema](https://glama.ai/mcp/schemas/server.json) defines a single required property, `maintainers`; no part of the build spec is expressible in the file itself

## [1.2.0] - 2026-08-13
### Fixed
- The server started only when its entrypoint was invoked by its real path, which meant `npx mcp-open-library` and a global install both exited 0 having done nothing. The guard read `process.argv[1] === new URL(import.meta.url).pathname`, and those two disagree under npm: a package's `bin` is linked into `node_modules/.bin` as a symlink and npm runs that path, so `process.argv[1]` is the link (`.../.bin/mcp-open-library`) while `import.meta.url` is the realpath of its target (`.../mcp-open-library/build/index.js`), because Node resolves symlinks for the main ESM module unless `--preserve-symlinks-main` says otherwise. The comparison could never hold, `run()` was never reached, and the process fell off the end of the module and exited successfully without printing anything. That is the worst shape this failure could take for an MCP server: the usual client config is `{"command": "npx", "args": ["-y", "mcp-open-library"]}`, so a client saw a server start, exit 0, and never speak protocol — a connection failure with nothing in the logs to explain it. Every documented route ran the file directly (`npm run inspector`, the Dockerfile `CMD`, Smithery's `node build/index.js`), which is why the bug survived. The comparison is now `realpathSync(process.argv[1]) === realpathSync(fileURLToPath(import.meta.url))` in `isMainModule` (`src/utils/main-module.ts`), the same fix the three release scripts in `scripts/` already carried. It resolves both operands rather than only `process.argv[1]`, which the scripts settle for: resolving the second is a no-op whenever the loader has already done it, and the point is not to depend on that — under `--preserve-symlinks-main` the loader leaves `import.meta.url` unresolved, and a one-sided comparison would fail there in exactly the way described above. Using `fileURLToPath` rather than `.pathname` fixes a second latent case: `.pathname` is percent-encoded, so a checkout under a path containing a space failed the comparison even without a symlink

### Changed
- The `bin` command and the MCP `serverInfo.name` are both now `mcp-open-library`, matching the package name, the npm identity and the `User-Agent` the HTTP clients already sent. The previous name, `open-library-server`, was a mistake. Retiring a published `bin` would normally be a breaking change, but this one never worked: every invocation route that consults `bin` goes through the symlink the fix above addresses. Nothing that runs today runs it. Smithery is unaffected — `smithery.yaml` invokes `node build/index.js` and does not consult `bin`

## [1.1.3] - 2026-08-13
### Security
- Transitive dependencies are now pinned to their [Socket registry](https://socket.dev/) drop-in replacements through `overrides` in `package.json`, with a matching `resolutions` block for Yarn and pnpm. 68 packages are declared, and the regenerated lockfile resolves 18 of them to `@socketregistry/*` — the other 50 are no longer in the tree at all. That is the substance of the change rather than a shortfall in it: the replacements are zero-dependency reimplementations, so the ES-shim micro-packages that existed only to satisfy one another fell out along with them, `es-abstract`, `call-bind`, `gopd`, `is-typed-array` and `which-typed-array` among them. Installed packages drop from 460 to 375 — the production tree from 108 to 92, the development tree from 352 to 283. Six replacements sit in the production tree (`es-define-property`, `es-set-tostringtag`, `hasown`, `object-assign`, `safer-buffer`, `side-channel`); the other twelve are dev-only, reached through the ESLint toolchain. The gain is that 85 fewer packages means 85 fewer maintainer accounts and publish pipelines able to reach an install, which is the surface a typosquat or a hijacked account actually travels through. Nothing changes at runtime, and nothing changes for anything installing this package — npm applies `overrides` only from the root project, never from a dependency's manifest

## [1.1.0] - 2026-08-10
### Added
- Tool: `search_books` - search across titles, authors, subjects, places, people, publishers and ISBNs, with `sort`, `language`, `limit` and `offset`. At least one search criterion is required
- `limit` and `offset` on `get_book_by_title` and `get_authors_by_name` — `limit` defaults to 10 with a maximum of 50, `offset` defaults to 0 with a maximum of 1000
- Requests now send a `User-Agent` identifying the server and its repository. (Open Library grants its higher 3 requests/second allowance only to clients that also send a contact email or phone number, so the default 1 request/second still applies here)
- Requests now time out after 15 seconds instead of hanging indefinitely
- Every tool now advertises a human-readable `title` and the `readOnlyHint` / `openWorldHint` annotations, which may allow a client to skip the confirmation prompt for these read-only lookups. Annotations are hints, and the MCP specification has clients treat them as untrusted unless the server is trusted, so the confirmation policy remains the client's decision
- Search results now carry `best_edition`: one edition of the work with its `isbn_13`/`isbn_10` where Open Library has them, plus its `edition_key`. Previously a search gave back only a *work* key, which no tool accepted — there was no route from a search result to an ISBN. The `edition_key` is an OLID that can be passed to `get_book_by_id` for the full edition record. ISBNs come from Open Library's nested `editions` sub-query rather than the work-level `isbn` field, which would return every edition's ISBN (6,113 for Pride and Prejudice) and inflate a page 35×

### Changed
- Invalid tool arguments now come back as a result with `isError: true` rather than a JSON-RPC `InvalidParams` error. The message is unchanged. Per the MCP specification, errors originating from a tool "SHOULD be reported inside the result object ... Otherwise, the LLM would not be able to see that an error occurred and self-correct" — a protocol error is raised by the client before the model ever sees it. Calling an unknown tool remains a protocol error, as the specification requires. Any unexpected exception inside a handler is likewise converted rather than escaping as a protocol error
- `get_book_by_title` returns an object `{ num_found, offset, limit, results }` rather than a bare array, so clients can tell how many matches exist beyond the page they were given. Previously it returned up to 100 results with no total
- `get_authors_by_name` returns an object `{ num_found, offset, limit, results }` rather than a bare array, and asks Open Library for one page instead of accepting its 100-result default. A broad name such as "smith" previously returned 100 authors — roughly 32KB into an assistant's context, against roughly 4.3KB for the default page of 10
- Search results now also carry `author_keys`, `ratings_average` and `ebook_access`. `author_keys` is an array of individual keys, each of which can be passed to `get_author_info` (which takes a single `author_key`)
- Search requests ask Open Library for only the fields used, cutting a typical `get_book_by_title` response from roughly 21KB to roughly 5.5KB
- `get_book_cover` and `get_author_photo` now check that the image exists and report `No cover image available ...` instead of returning a URL that resolves to a blank placeholder
- Upstream failures report a consistent `Open Library API error: <status> <reason>` including the HTTP status code, and all tools now set `isError` on failure (`get_book_by_id` previously did not)
- `get_book_by_id` flags both of its not-found paths the same way. Open Library reports a missing identifier either as a 404 or as a 200 carrying an empty record set; the latter previously came back without `isError`, so one outcome had two shapes
- `search_books` requires `language` to be a lowercase three-letter MARC code. Values such as `123` or `ENG` were previously forwarded to Open Library, which answered with no matches rather than reporting the code as malformed
- `get_book_cover` no longer accepts an explicit `size: null`; omit `size` to get the default `L`
- Each tool's JSON Schema is generated from its zod schema, so what clients are told a tool accepts can no longer drift from what is enforced

### Fixed
- `get_book_cover` and `get_author_photo` no longer report a cover as available when the request to the covers service actually failed. The existence check suppressed every HTTP status, so a 429 or 500 was indistinguishable from a hit and produced a URL; only a 404 now means "no image", and any other failing status is reported as an error
